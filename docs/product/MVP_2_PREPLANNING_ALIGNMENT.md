## 2. 修正先前假设

先前 README、PROGRESS、收尾记录及研究建议中的“配对案例”“参考匹配”是信息不完整时的后续设想。
用户澄清后，**不再把恢复两份数据的同一案例对应关系作为默认目标**。
原收尾和研究记录保留原文，通过后续说明链接到本文件，避免改写当时历史。

讨论时分别处理：

- **身份解析**：是否指向同一个具体对象；不能把独立案例中的相似名称视作同一对象。
- **语义相似**：组件类别、功能或失效描述可能相似，仍不足以证明可直接应用。
- **知识适用性**：历史知识能否用于当前目标，需要工程上下文和可追踪依据；不可确认时保留未知或无匹配。

这些是避免错误解读的概念区分，不是已冻结的类、算法或输出 schema。
Spec 中实体解析、上下文重建和评测部分需要在信息对齐后审查，不能直接照旧开始实现。

### 9.1 路线取舍建议（待确认）

可选路线的比较：继续严格按原阶段顺序最容易控制范围，但近期无法展示完整用户体验；
直接把全部愿景塞进一个 MVP 会同时引入文档摄取、跨源协调、生成、UI 和知识更新，难以界定验收。
**助手推荐：保留检索模块的独立验证，在现有架构上增加小范围端到端 Demo 里程碑。**
它复用 CSM、LangGraph 和端口；只覆盖一个明确案例、少量输入格式、候选报告及简单 UI。
如何命名阶段、何时接入 LLM/文档读取、是否增加候选知识暂存，待修订 Spec 后确定；
现有 MVP-2 的不引入真实 LLM、UI、写回等草案限制不能被默默改成已批准扩展。

建议演示流程：上传资料 → 展示识别到的系统/部件/功能及来源 → 补问关键工况 →
自动只读检索 → 生成候选失效/影响/起因/措施 → 显示证据和缺失项 → 导出候选 FMEA 报告。
首版可提出支持可提取文本的 PDF、固定列 BOM 表格、已验证单文件 SysML 子集；
具体格式与数量需先看首个资料包，不承诺通用扫描件、图纸或复杂多文件模型解析。
资料之间若型号/版本/对象不一致，应提示分开处理，不为完成报告强行拼成同一系统。
现有独立的 SysML 与 Neo4j 仍不得假定配对。

候选报告建议包含：分析范围/版本、结构与功能摘要、失效模式、起因、影响、
原有控制、建议措施、来源定位、证据状态、待确认事项、风险未评估说明。
原有控制必须来自资料；新增措施标为建议；缺少事实/授权规则时保留 UNKNOWN / NOT_EVALUATED。
“报告结构完整”不等于“所有工程结论完整正确”或“已获批准”。

### 9.2 三个需保持明确的语义边界

1. **可靠性提示。** 建议先展示字段级来源（模型/文档事实、历史知识、模型推断）、
   适用条件缺失及审核状态；未校准前不显示诸如 90% 的工程正确率。
   若后续采用检索相似度，必须按相似度命名，不能等同于适用概率或来源权威性。
2. **无匹配与推理。** 无适用知识时保留无匹配结果；后续生成阶段可基于已知事实给出
   参考性推断、假设及建议验证方法，不能把推断标成检索命中。连接故障另报错误。
3. **知识积累。** 建议逐步保存来源、候选分析和人工修改，并仅将经过明确审核的适用知识
   提升为可复用条目；保留对象、工况和版本。不是对话一次就训练模型或自动修改现有 Neo4j。
   候选暂存、审核入库和模型训练是不同能力，本次仅讨论，均未实现。

### 9.3 用现有材料减少测试准备

| 材料 | 可以自动准备的测试 | 不能据此宣称验证的内容 |
|---|---|---|
| 已有 SysML 与独立核对的期望快照 | 部件/功能/来源提取、显式缺失、格式和流程回归 | 真实失效模式、起因、措施的完整工程正确性 |
| 原始 Excel 和经过核对的图对应记录 | 命中定位、来源字段、缺失/重复处理的参考样例 | 未完成对账的图路径具有行级来源；对新系统适用 |
| 人为构造的缺失/冲突/不存在标识样例 | 输入错误、补问、无结果状态、歧义和异常处理 | 随机改名即证明工程不适用；任意跨案例负样本都成立 |
| LLM 生成的 FMEA 草案 | 演示、候选测试题、结构/字段检查 | 独立工程 gold 或与自己的答案一致即证明正确 |

可从 SysML 派生演示用 BOM/设计说明，但必须标注派生来源和人工补充假设，
不得虚构模型未表达的物料数量、材料或工况；这些资料彼此同源，不能作为独立交叉验证。
建议由助手准备大部分样例和预期结果，人只核对少量关键工程判断。
检索测试允许知识留在库中验证“找回”；生成泛化测试需隔离参考答案，按原始案例/来源划分，
不能把同一模型的改名副本分别放入训练与测试后声称泛化有效。
